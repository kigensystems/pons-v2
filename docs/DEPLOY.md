# Deploying Plum

Prepared September 8, 2026; provider facts re-checked against the hosts' documentation on September 9, and deployed that evening. Netlify project `pluminfra` (team Kigen, renamed from `plumdesk`) serves the frontend at `https://pluminfra.xyz` (also `pluminfra.netlify.app`) and proxies `/api` to the launch API, one Docker container with a persistent disk on Render at `https://plum-api-fg3l.onrender.com`. Both build from `main` on every push. This is the checklist that was followed, kept for the next environment.

## Shape

- **Frontend**: Netlify builds `frontend/` (`netlify.toml`). The same file holds the redirects: `/api/*` proxied to the Render origin with status 200 and `signed = "PLUM_PROXY_SECRET"`, then the single-page fallback. The proxy keeps the API same-origin for the browser, so the HttpOnly session cookie and the API's `Origin` check work unchanged. Signing means Netlify adds an `x-nf-sign` JWS (HMAC SHA-256, issuer `netlify`, short expiry) to every proxied request; the API refuses any request without it except `/api/health`, so the Render hostname cannot be used to reach around the site's rate limits. Netlify only supports `signed` in `netlify.toml`, so the Render hostname is written there rather than read from an environment variable.
- **API**: `backend/Dockerfile` (Node 24, `npm ci --omit=dev`, `src/server.ts`). `render.yaml` at the repository root is a Render Blueprint: one web service on the `0.5c-512mb` instance (Starter, $7 a month, does not sleep; only Render's free instances spin down after 15 idle minutes), health check on `/api/health`, a 1 GB disk at `/data` for the SQLite file and uploads. `PLUM_HOST=0.0.0.0` makes the server reachable inside the container; `PLUM_TRUST_PROXY=1` keys rate limits on the browser's address as Netlify forwards it in `x-nf-client-connection-ip` (`X-Forwarded-For` as the fallback).
- **Secrets** stay in the hosts' dashboards. The only browser-visible value is `VITE_REOWN_PROJECT_ID`.

## Steps

1. **Render.** New → Blueprint → this repository. Render reads `render.yaml`. Fill the `sync: false` values: `ROBINHOOD_RPC_URL` (the Alchemy mainnet URL), `MOBULA_API_KEY`, `PLUM_ORIGIN` and `PLUM_PUBLIC_URL` (both the Netlify site URL, `https://<site>.netlify.app` or the custom domain, no trailing slash), `PLUM_PROXY_SECRET` (any long random string, for example `openssl rand -base64 48`). `SESSION_SECRET` is generated. Note the service URL; the blueprint asks for `plum-api`, so Render assigned `https://plum-api-fg3l.onrender.com`, which is what `to` in `netlify.toml` names.
2. **Netlify.** Add site from Git → this repository; `netlify.toml` sets base, command, publish and the redirects. Environment: `VITE_REOWN_PROJECT_ID`, and `PLUM_PROXY_SECRET` with exactly the value given to Render and its scope including **Runtime** (the signature is computed at request time, not at build time). Deploy.
3. **Reown.** At dashboard.reown.com add the Netlify origin to the project's allowed domains. An origin not on the list is refused outright (AppKit error APKT002), not warned about.
4. **Check** on the live site: `/api/health` answers through the proxy and its `client` field is your own public IP, not a Netlify or Render address (if it is, every visitor shares one rate limit; see Boundaries); `https://plum-api-fg3l.onrender.com/api/launch-config` fetched directly answers 403 `unsigned`, which proves the proxy secret is set on both sides; the Explore CRT shows the latest graduation; Connect wallet → sign in → the header shows the address (this proves the proxied `Origin` header and cookie survive Netlify); open Create a coin and read the live terms. Stop before signing a transaction unless a real launch is intended.
**Done on September 9:** step 4 passed, first through the netlify.app address and then on the domain once its nameservers reached the resolvers: `/api/health` through the proxy reported the caller's own address; a direct call to the Render hostname answered 403 `unsigned`; a scripted wallet ran challenge → verify → session → launch-config → intent through the proxy, with the `Set-Cookie` (HttpOnly, Secure) surviving Netlify and a request from the `netlify.app` origin refused as `bad_origin`; Explore rendered with the live spotlight and every API call 200. The user then ran Rabby on `https://pluminfra.xyz/explore`: connect, sign in, the address survived repeated reloads, Create a coin → Review returned a real quote and a real simulation (`insufficient_funds`, the wallet holds no ETH on Robinhood Chain), and the sign button stayed disabled. Rabby shows a caution on connect because the domain was registered that day; its new-domain rule lasts 30 days, and its Discord is the route onto its dapp list. Only a mined launch remains unproven; it needs about 0.003 ETH on Robinhood Chain in the launching wallet.

5. **Domain.** If a custom domain is added later, pick one canonical host (apex or `www`), let Netlify redirect the other to it, and set `PLUM_ORIGIN` to the canonical one. The sign-in message and the write-origin check are bound to that exact host.

## Boundaries

- One Render instance. Rate limits and the spotlight cache are per process; the intents worker must not run in two instances against one database. Render does not allow more than one instance for a service with a disk, which matches; a bigger single instance (`1c-2g` and up in `render.yaml`) is the way to grow.
- Uploads live on the Render disk and are served from `PLUM_PUBLIC_URL/api/uploads/<id>` through the Netlify proxy. Token logos written onchain point at that URL, so the site must stay up for them to resolve; an IPFS pin behind the `ImageStore` adapter is the durable alternative. The upload responses are immutable and cacheable, so Netlify's CDN can hold them.
- The Netlify proxy forwarding `Origin` and `Cookie` is expected (Netlify staff state cookies pass unmodified) but only proven by step 4. If sign-in returns 403 `bad_origin`, the proxy dropped the header; the fallback is a custom domain for the API on the same site (`api.<domain>`) with `PLUM_ORIGIN` unchanged and the cookie moved to `SameSite=None; Secure`.
- A service with a disk restarts in place on deploy, so each deploy is a few seconds of downtime; intents in flight survive in SQLite and reconcile when the worker returns. Render restarts an instance that fails its health check for 60 s.
- Netlify ends a proxied request after 26 s. The API's RPC timeout is 10 s with retries, so a provider outage surfaces as the API's own 502 rather than Netlify's. Netlify documents no body-size limit for proxied requests; uploads are capped at 2 MB by the API and the 2 MB case is the first thing to try on the live site.
- Netlify does not cache proxied JSON (the API sends `Cache-Control: no-store`) and has no default per-visitor rate limit; the API's own limits are the protection. Netlify's own rate-limiting rules can be added per redirect if needed.
- **Traffic and bills.** The Netlify account is on the Personal plan ($9 a month, 1,000 credits, no rollover, auto-recharge of 500 credits for $5; September 9). A user-owned private repository builds on it; only private organization repositories need Pro. Credits go to bandwidth at 20 per GB, production deploys at 15 each, and web requests at 2 per 10,000. A first visit to the opening scene downloads about 10 MB (the Macintosh model is 5 MB, the channel videos 2.4 MB, images 2.5 MB), so 1,000 credits is roughly 5,000 first-time visitors a month less 15 per push to `main`; Explore alone is far lighter. With auto-recharge off the site pauses when credits run out and shows "Site not available", so turn auto-recharge on before launch day. Pro ($20, 3,000 credits) is cheaper once recharges pass about four a month. Render's Starter workspace includes 5 GB outbound a month, then a per-GB fee; API responses are small, and logos are the only large responses.
- **RPC provider.** The Alchemy account moved to pay-as-you-go on September 9: 10,000 compute units and 300 requests a second, $0.45 per million units, no monthly fee, with a usage cap set in Billing so the account stops rather than overspends. Throughput is per account, not per app, and only Plum uses this account. The API's reads leave through a gate of sixteen at a time with backoff on 429; 100 simultaneous creators signed in and prepared in 0.7 s and 300 in 1.5 s against this plan, with no refusals, while viewers never reach the provider because settings, fees, the spotlight and protocol state are cached and shared. One sign-in costs one `eth_call`; one prepared launch costs three reads; the worker costs about two reads every five seconds per unsettled transaction, with backoff for hashes the network has not seen. For scale: the Free plan (300 CU/s, 30M a month) sustained about 40 contract reads a second and would serve the same 100-creator burst in about 4 s in waves.
- **Live events.** The API keeps one WebSocket to Alchemy (derived from `ROBINHOOD_RPC_URL`; set `PLUM_RPC_WS_URL` to choose another) for factory logs. Render web services hold long-lived outbound connections without special settings; the subscription costs a few compute units a minute. `eth_subscribe` traffic shows in Alchemy's dashboard as WebSocket usage.
- **Reown.** The free project allows 500 monthly active wallets and 2.5 million RPC calls a month through Reown's relay; a launch that connects more wallets than that needs the Pro plan ($89 a month, 7,500 wallets). AppKit 1.8.23 is the current release for both packages as of September 9, 2026.

## Headers and the publish

`netlify.toml` sets `Cache-Control` per path: `/assets/*` (hashed) immutable for a year, `/fonts/*` a week, `/images/*` and `/videos/*` a day with stale-while-revalidate. Every response also carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, a referrer policy and a permissions policy; the live site cannot be framed, so mobile checks through a scratch iframe page work only against the local dev server. The build command deletes `dist/models` so the licensed Macintosh model, tracked for the Three.js comparison view, is not published, and copies `dist/index.html` to `dist/404.html`. Only `/explore`, `/launch` and `/about` are redirected to the shell with a 200; Netlify serves `404.html` with a 404 status for every other missing path, and the app renders its not-found page on it. After a deploy `https://pluminfra.xyz/models/macintosh-512k.glb` and `https://pluminfra.xyz/nothing` should answer 404 while `/about` answers 200.
