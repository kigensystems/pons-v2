# Deploying Plum

Prepared September 8, 2026; provider facts re-checked against the hosts' documentation on September 9. Netlify serves the frontend and proxies `/api` to the launch API, which runs as one Docker container with a persistent disk on Render. Nothing has been deployed yet; this is the checklist.

## Shape

- **Frontend**: Netlify builds `frontend/` (`netlify.toml`). The same file holds the redirects: `/api/*` proxied to the Render origin with status 200 and `signed = "PLUM_PROXY_SECRET"`, then the single-page fallback. The proxy keeps the API same-origin for the browser, so the HttpOnly session cookie and the API's `Origin` check work unchanged. Signing means Netlify adds an `x-nf-sign` JWS (HMAC SHA-256, issuer `netlify`, short expiry) to every proxied request; the API refuses any request without it except `/api/health`, so the Render hostname cannot be used to reach around the site's rate limits. Netlify only supports `signed` in `netlify.toml`, so the Render hostname is written there rather than read from an environment variable.
- **API**: `backend/Dockerfile` (Node 24, `npm ci --omit=dev`, `src/server.ts`). `render.yaml` at the repository root is a Render Blueprint: one web service on the `0.5c-512mb` instance (Starter, $7 a month, does not sleep; only Render's free instances spin down after 15 idle minutes), health check on `/api/health`, a 1 GB disk at `/data` for the SQLite file and uploads. `PLUM_HOST=0.0.0.0` makes the server reachable inside the container; `PLUM_TRUST_PROXY=1` keys rate limits on the browser's address as Netlify forwards it in `x-nf-client-connection-ip` (`X-Forwarded-For` as the fallback).
- **Secrets** stay in the hosts' dashboards. The only browser-visible value is `VITE_REOWN_PROJECT_ID`.

## Steps

1. **Render.** New → Blueprint → this repository. Render reads `render.yaml`. Fill the `sync: false` values: `ROBINHOOD_RPC_URL` (the Alchemy mainnet URL), `MOBULA_API_KEY`, `PLUM_ORIGIN` and `PLUM_PUBLIC_URL` (both the Netlify site URL, `https://<site>.netlify.app` or the custom domain, no trailing slash), `PLUM_PROXY_SECRET` (any long random string, for example `openssl rand -base64 48`). `SESSION_SECRET` is generated. Note the service URL; the blueprint asks for `plum-api`, so it is `https://plum-api.onrender.com` unless the name was taken, in which case edit `to` in `netlify.toml` before step 2.
2. **Netlify.** Add site from Git → this repository; `netlify.toml` sets base, command, publish and the redirects. Environment: `VITE_REOWN_PROJECT_ID`, and `PLUM_PROXY_SECRET` with exactly the value given to Render and its scope including **Runtime** (the signature is computed at request time, not at build time). Deploy.
3. **Reown.** At dashboard.reown.com add the Netlify origin to the project's allowed domains. An origin not on the list is refused outright (AppKit error APKT002), not warned about.
4. **Check** on the live site: `/api/health` answers through the proxy and its `client` field is your own public IP, not a Netlify or Render address (if it is, every visitor shares one rate limit; see Boundaries); `https://plum-api.onrender.com/api/launch-config` fetched directly answers 403 `unsigned`, which proves the proxy secret is set on both sides; the Explore CRT shows the latest graduation; Connect wallet → sign in → the header shows the address (this proves the proxied `Origin` header and cookie survive Netlify); open Create a coin and read the live terms. Stop before signing a transaction unless a real launch is intended.
5. **Domain.** If a custom domain is added later, pick one canonical host (apex or `www`), let Netlify redirect the other to it, and set `PLUM_ORIGIN` to the canonical one. The sign-in message and the write-origin check are bound to that exact host.

## Boundaries

- One Render instance. Rate limits and the spotlight cache are per process; the intents worker must not run in two instances against one database. Render does not allow more than one instance for a service with a disk, which matches; a bigger single instance (`1c-2g` and up in `render.yaml`) is the way to grow.
- Uploads live on the Render disk and are served from `PLUM_PUBLIC_URL/api/uploads/<id>` through the Netlify proxy. Token logos written onchain point at that URL, so the site must stay up for them to resolve; an IPFS pin behind the `ImageStore` adapter is the durable alternative. The upload responses are immutable and cacheable, so Netlify's CDN can hold them.
- The Netlify proxy forwarding `Origin` and `Cookie` is expected (Netlify staff state cookies pass unmodified) but only proven by step 4. If sign-in returns 403 `bad_origin`, the proxy dropped the header; the fallback is a custom domain for the API on the same site (`api.<domain>`) with `PLUM_ORIGIN` unchanged and the cookie moved to `SameSite=None; Secure`.
- A service with a disk restarts in place on deploy, so each deploy is a few seconds of downtime; intents in flight survive in SQLite and reconcile when the worker returns. Render restarts an instance that fails its health check for 60 s.
- Netlify ends a proxied request after 26 s. The API's RPC timeout is 10 s with retries, so a provider outage surfaces as the API's own 502 rather than Netlify's. Netlify documents no body-size limit for proxied requests; uploads are capped at 2 MB by the API and the 2 MB case is the first thing to try on the live site.
- Netlify does not cache proxied JSON (the API sends `Cache-Control: no-store`) and has no default per-visitor rate limit; the API's own limits are the protection. Netlify's own rate-limiting rules can be added per redirect if needed.
- **Traffic and bills.** Netlify bills bandwidth from a credit pool (20 credits per GB; Free has 300 credits with a hard stop, Pro from $20 a month with auto-recharge). When credits run out the site shows "Site not available", so for a launch day put the site on a paid plan with auto-recharge on. Render's Starter workspace includes 5 GB outbound a month, then a per-GB fee; API responses are small, and logos are the only large responses.
- **RPC provider.** The Alchemy account is on the Free plan: 30M compute units a month and a 300 CU/s throughput cap, per its billing page on September 9. Probing the key that day, `eth_call` sustained at 40 a second for 8 s with no refusals and at 80 a second was refused more than half the time, while the dashboard's peak-throughput meter read 277 of 300 CU/s, so Alchemy meters these reads at well under the 26 CU the price list names and the practical ceiling is roughly 40 to 60 contract reads a second. Throughput is per account, not per app, and only Plum uses this account. The API's reads leave through a gate of eight at a time with backoff on 429, about the same rate as that ceiling, so a burst of creators is served in waves (100 simultaneous quotes took 3.9 s) rather than failing; viewers never reach the provider because settings, fees, the spotlight and protocol state are cached and shared. One sign-in costs one `eth_call`; one prepared launch costs three reads; the worker costs about two reads every five seconds per unsettled transaction, with backoff for hashes the network has not seen. The month's 30M units are not a concern: the probes used under 100,000. Pay-as-you-go raises throughput to 10,000 requests a second at $0.45 per million units with no monthly fee; its Billing settings take a usage limit in dollars or units at which Alchemy stops serving rather than charging more, and the upgrade places a $5 card hold that Stripe releases within about a week. A busy launch day is the reason to switch, with that limit set first.
- **Reown.** The free project allows 500 monthly active wallets and 2.5 million RPC calls a month through Reown's relay; a launch that connects more wallets than that needs the Pro plan ($89 a month, 7,500 wallets). AppKit 1.8.23 is the current release for both packages as of September 9, 2026.
